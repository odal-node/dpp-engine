# 0.17.0 verification record

Every pull request merged since v0.16.0 is traced to the CHANGELOG entry that describes it. Every entry's claims are checked against the code at the release commit. Every issue those pull requests closed is checked against what it asked for. Corrections land in `CHANGELOG.md` in the same change as this record, before the tag. `docs/governance/RELEASE.md` makes this record a step of every release.

- **Range:** `v0.16.0` (`3765ec18`) to `main` at `7df12d25`.
- **Checked against:** `main` at `7df12d25`, which holds every pull request below. The release commit adds the version bump, the date, and the standards re-read: all 28 IETF rows of `docs/architecture/STANDARDS.md` matched the RFC Editor's index on 2026-11-25, and the GS1 resolver standard's latest release is still 1.2.1. The change that carries this record corrects two entries of `CHANGELOG.md` and adds two tests: `a_category_an_earlier_schema_allowed_is_accepted` (`crates/dpp-vault/src/handlers/credentials.rs`), for E13, and `integers_past_what_signing_holds.rs` (`crates/dpp-vault/tests`), for #600.
- **Date:** 2026-11-25.

## How each claim was checked

A claim is **verified** when the code at the commit above does what it says. Evidence is one of:

- the source location that implements it;
- a test that pins it, by name. Every test named below, but the one this change adds, is in a suite that passed in the `CI` workflow on `main` at `7df12d25`: the unit tests of the workspace, and the integration tiers of `dpp-dal`, `dpp-vault`, `dpp-plugin-host` and `dpp-node`. The added test passed locally, and failed when the handler read only the current schema's categories, as it did before this release.

Three verdicts are used, and only the first is a finding that the whole entry is true:

- **Verified:** the source and a named test both found, and they say what the entry says.
- **Verified in part:** the same, for all of the entry but the claims the row names as unmatched.
- **Corrected:** the entry said something the code does not do, or that a later pull request in the same release changed. The CHANGELOG now says what is true, and the row says how it differed.

Every backticked path and identifier in the `[Unreleased]` section was also checked mechanically, to confirm it exists outside the CHANGELOG. Of 159, 21 do not appear verbatim, and all 21 are legitimate:

- `0050_obligation_notice.sql`, a file name: it is `ops/pg/0050_obligation_notice.sql`;
- `EvidenceDossierRepository::get` and `TransferStore::get_chain`, written as `Type::method`, which the source spells as a trait method, and `Caller::get_module_export`, a `wasmtime` function named by the advisory entry, in a dependency;
- `wasmtime-wasi-http`, a crate the advisory names as affected. `Cargo.lock` holds no package of that name;
- five things this release removed or refuses, quoted to describe the old behaviour: `DerogationRef`, `--derogation-citation`, `GET /vault/api/v1/unsold-goods`, `POST /vault/api/v1/unsold-goods` and `productGroup: unsold-goods`;
- four routes written under the `/vault` prefix the node mounts: `PATCH /vault/api/v1/operator`, `POST /vault/api/v1/dpp/validate`, and the `eol` and `personal-data` routes of `/vault/api/v1/dpp/{dppId}`;
- `manufacturer.didWebUrl`, `materials[].countryOfOrigin` and `materials[].recycledPct`, JSON paths into the API description;
- three request bodies written as examples: `{"field", "content"}`, `{"otherUnionLaw": {"citation": "..."}}` and `{"responsibility": {"role": …, "basis": …}}`;
- `odal unsold-goods record <file>`, a command line with a placeholder. The command is `UnsoldGoods` `Record` in `cli/src/cli_args.rs`.

**Entries corrected:**

- **`dpp-core` 0.24.0: the resolver's authority view no longer carries `jwsSignature` (E07):** the resolver has no authority view to change. It serves the public view whatever the request says (`parse_access_tier` returns `Audience::Public`, `crates/dpp-resolver/src/handlers/resolve_json.rs:121`), and re-attaches `publicJwsSignature`. The credentialed read is where an authority's view is served, and it already carried no `jwsSignature` at v0.16.0: `no_view_carries_a_proof_it_does_not_cover` (`crates/dpp-vault/src/handlers/audience_read.rs`) is in that file at the tag, over the public, legitimate-interest and authority views. It carries `disclosureJwsSignature`, the proof over the view it serves (`a_non_public_view_is_served_with_a_proof_that_covers_it`). No view this node serves changed, so the entry was not a breaking change. It repeated the repin issue's table, which named the resolver's authority tier, and closed on "open on #600", an issue that is now closed. The entry is under **Changed**, says that no view changes, and no longer says the question is open.
- **`dpp-core` 0.24.0: unsold goods is no longer a product group (E06):** it said the unsold-goods disclosure route "is unchanged until #597 replaces it". #632, in this release, replaced it (E08). The entry now says so.

**Found while checking, outside the changelog:**

- **A review finding turned out to be unreachable.** A reviewer said a draft stated at create could be signed on a blank operator name. The route refuses an incomplete operator identity before publish is reached (`crates/dpp-vault/src/handlers/publish.rs:49`), for every product group, and `a_stated_draft_is_not_signed_on_a_name_the_operator_has_lost` pins it.
- **The integer check the repin issue (#600) listed is now a test, and finds nothing to fix.** It asked whether any numeric field an operator can declare carries an integer beyond 2^53 − 1, because core 0.24.0 refuses one at signing. `crates/dpp-vault/tests/integers_past_what_signing_holds.rs` puts three such integers into every number of every frozen stored document and every shipped demo passport's `productGroupData`, reads the result, and serialises and canonicalises it the way publish does. Every typed field either refuses the integer on read or takes it as a float that canonicalises. The one place free-form JSON reaches a passport is a product group core has no typed variant for, which carries its data verbatim; the retired `unsold-goods` document is one, and `validate_passport` refuses it before publish signs anything, which the test asserts. The first run of the walk, before that case was handled, failed on exactly that document and no other, so the walk does find a value that reads and cannot be signed. The end-of-life summary, the other free-form field, is guarded on its own route (E20).
- **A credential narrowed to a withdrawn product category is no longer refused (E13).** The v0.16.0 record named this as a finding. This release fixed it and had no test that names a withdrawn value; this change adds one.
- **Five of E16's six description corrections have no test named for them.** The `500` on a publish whose signing fails, the empty `country` of an unconfigured operator, the nullable manufacturer and material fields, the health bodies and the `422` body of an uploaded dossier are in the description and match the code. The checking client pins one only when some vault test receives that response. The sixth, the `?schema_view` body, has `a_schema_view_is_served_as_documented_on_both_public_reads`.
- **The removal of `GET /vault/api/v1/unsold-goods` is pinned by the router, not by a test (E08).** `the_removed_line_route_is_gone` posts to the removed route and asserts `404`. No test sends the `GET`. The router has no route for it.
- **A node with `OBLIGATION_NOTICES` off announcing nothing is pinned by its source (E11).** The task is spawned only `if obligation_notices_enabled()` (`crates/dpp-node/src/main.rs:518`), and `the_switch_is_on_only_for_on` tests the parse. No test boots a node with the switch off.
- **#375's premise, "nothing is broken today", was false.** The resolver filtered the envelope with a policy that opens nothing, so a battery passport at schema 2.7.0 or later was served without `batchId` and `serialNumber` and with a proof over the full view. #653 found it before documenting the filter, and fixed it (E22).
