# 0.16.0 verification record

Every pull request merged since v0.15.0 is traced to the CHANGELOG entry that describes it. Every entry's claims are checked against the code at the release commit. Every issue those pull requests closed is checked against what it asked for. Corrections land in `CHANGELOG.md` in the same change as this record, before the tag. `docs/governance/RELEASE.md` makes this record a step of every release.

- **Range:** `v0.15.0` (`6733e9f8`) to `main` at `d360b409`.
- **Checked against:** `main` at `1f32e7b7` for E01 to E29, at `3278066b` for E30 to E43, the entries of the five pull requests merged after it, and at `d360b409` for E44 (#612). The release commit adds the version bump and moves six breaking changes under **Breaking**, each with a migration note and its claims unchanged: E13, E18, E31, E35, E36, and E41's refusal of plain HTTP to a remote host.
- **Date:** 2026-11-12, extended 2026-11-13 and 2026-11-14.

## How each claim was checked

A claim is **verified** when the code at the release commit does what it says. Evidence is one of:

- the source location that implements it;
- a test that pins it, by name. Every test named below is in a suite that passed on 2026-11-12 on `main` with #576 merged in: `just check`, and the `dpp-dal`, `dpp-vault`, `dpp-plugin-host` and `dpp-node` integration tiers. The tests named for E30 to E43 also passed on 2026-11-13: in `just check` on `main` at `3278066b` with this record merged in, and in the CI of the pull request that added each, including the testcontainers tier and both images. The tests named for E44 passed on 2026-11-14, in `just check` on `main` at `d360b409` with this record merged in, and in #612's CI;
- the upgrade and onboarding paths, which `operator_paths.rs` runs on every pull request against the real binaries.

Every backticked path and identifier in the section was also checked mechanically, to confirm it exists outside the CHANGELOG. Of 150, nine do not appear verbatim, and all nine are legitimate:

- five routes, which appear in the API description under the `/vault` prefix the node mounts;
- `complianceResult.repairabilityIndex`, a path into a schema that defines `repairabilityIndex`;
- `odal.passport_transfer.revision`, the column `0047_passport_transfer_revision.sql` adds;
- `Caused by:`, the label `anyhow` prints, quoted to describe the old behaviour.

The 46 in E30 to E44 were checked the same way. Six do not appear verbatim, and all six are legitimate:

- `could not reach the node at <origin> (<reason>)`, `key:<id>` and `user:<id>`, messages and keys the code builds with `format!`;
- `odal key create --scope read|write|admin` and `odal passport import --product-group <key>`, command lines with placeholders;
- `InvalidCheckDigit { .. }`, quoted to describe the old output.

**Entry corrected:**

- **A submission past the first thousand tasks on the dashboard is found (#484):** it said a long task list "is now read from both ends, interleaved, since the order is not recorded". #490, in the same release, asks the registry for newest first and reads from the front once the first page proves that order. Both ends are read only when the order cannot be told. The entry now says so and points at the **Changed** entry.
- **Pointing a profile at another node clears the credential the previous node issued (#576):** only the guided setup does. `step_connect` (`cli/src/console/setup.rs:43`) removes the key when it moves the active profile to this machine's node. `odal profile create <name> --force` over an existing profile replaced its URLs and left the key stored under that name (`cli/src/config/profiles.rs:304` at `3278066b`), and the next command sent it to the new node. The entry now names the guided setup, and #612 (E44) closes the `--force` path. See *Found while checking*.

**Found while checking, outside the changelog:**

- **The standards register's RFC 3279 row omitted the specification that RFC obsoletes.** The RFC Editor's page lists it. Corrected in the same change, which is also this release's re-read of the register (step 7 of the checklist). Every other row matched its source and its `Read` date is now 2026-11-12. The GS1 row still names 1.2.1, the latest release listed.
- **A credential narrowed to a withdrawn product category is refused at issuance.** Category-scoped issuance (#507) checks the requested values against the current schema's list, so a value that only an earlier schema version allows (an electronics `laptop` from before `v1.2.0`) is refused, although stored passports state it. The entry's description of the check is accurate for this release. The list of every version's values is a dpp-core change, and the switch to it is part of the dpp-core 0.24.0 repin (#600).
- **`odal profile create --force` carried a key to a node that never issued it.** The credential store is keyed by profile name, and overwriting a profile did not clear its entry, so a profile re-pointed this way sent the previous node's key to the new one. It predates #576, which closed the same path in the guided setup only. Fixed in this release by #612 (E44): the key is kept only while the vault URL is unchanged.
- **Three behaviours are pinned by their source, not by a test that exercises them.** The refusal of a cross-origin Basic credential (E35): the predicate it reads is tested, the branch that refuses is not. The rule that a CA path pass only through certificates that may sign certificates (E37): `may_issue_certificates` (`crates/dpp-seal/src/cades/path.rs:235`) is called from the path walk, and no test builds a path through a certificate that may not. The escaping of a plugin's log text (E39), done by formatting it with `Debug`. Each entry is accurate; a regression in any of the three would pass the tests.
- **`odal verify` on the file `odal passport evidence -o` writes is tested against a stub node only (E33).** The CLI re-serialises the dossier it unwraps. The node's checks compare canonical (JCS) forms, so a re-serialised dossier should verify, but no test sends one to a real node.
